# Common-source generalization completion

T-0236 closes the working path introduced by T-0235: edit a common array source,
check it, automatically partition it, execute on the existing QEMU/RTL backend,
inspect saved outputs and compare runs. The language and ceilings are the explicit
ADR-0132 contract. A completed supported workflow is distinct from adding every
future numerical type, dynamic control construct or model importer.

## Completion checklist

| Obligation | Verification |
| --- | --- |
| No workload-specific RTL or hand partitioning | Long24-node expression and nine-live-value map use unchanged kernel/runtime and automatic passes. |
| Shape-independent lowering | Pointwise1x3 and17x19; two GEMM shapes;64x64 broadcast; transpose. |
| All declared operators and composition | add, mul, unsigned max, add_imm, ge_imm, signed max, ReLU; sum/max folds; post after wrapped fold; fanout/join. |
| Cardinality boundaries | Eight inputs/views and eight stages/requested outputs; other static ceilings and rejection paths in UT. |
| Failure and fresh retry | Actual wrong-word and RTL-fault failures stop at the selected middle pass and publish no parent outputs; fresh successful attempts preserve failed evidence. |
| Cancellation boundary | Real device cancellation leaves the coupled parent unsealed because changed execution options are rejected; this is not a public array-cancellation protocol. |
| Independent result checking | Owned hand-derived formulas, separate whole-source scalar interpreter and actual nested RTL/guest proofs. |
| Saved inspection | All complete/incomplete parents revalidate without process creation; the unsealed cancellation remains visible as unsealed. |
| Repeatability | Exact commands, source/kernel/runtime identities, raw logs and nested receipts retained; no hardware purchase or new environment dependency. |
| Normal usage | One public CLI and editable JSON examples; see ARRAY_PROGRAM.md. |

The functional campaigns are implemented in `scripts/array_program_acceptance.py`
and `scripts/array_program_system_checks.py`. Their expected values are source-level
formulas, not generated by the pass compiler. Each positive case calls the same
`python3 -m raveil project array-run` entry that an edited user file uses. Injection
wrappers delegate to real execution. The acceptance harness is not an execution
backend and supplies no workload special case to the compiler.

## Replay

Use a verified existing MF01 kernel and runtime, then run from this checkout:

```sh
python3 -m unittest -v tests.test_array_program tests.test_project_array tests.test_array_program_acceptance
python3 -B scripts/array_program_acceptance.py --output /tmp/array-acceptance-new --kernel /path/to/sonatine.elf --build /path/to/verified-runtime
python3 -B scripts/array_program_system_checks.py --output /tmp/array-system-new --kernel /path/to/sonatine.elf --build /path/to/verified-runtime
```

Choose fresh output directories; earlier captures are never overwritten. These
commands require the same existing QEMU executable and offline Docker runtime as
other MF01 workflows. Hardware implementation, commercial hardening, speed/energy
claims and Groq comparisons are not established by functional simulation.

## Evidence interpretation

Session/job counts count verified sealed DAG receipts; a cancelled unsealed
execution is reported separately. The original acceptance campaign checks the
failed captured-content inventory and saved reinspection. The supplementary
campaign additionally compares the full failed tree including parent seals.
Logical plane limits are not an RSS bound; capture reservations are not a promise
about all future log sizes. Exact source/resource/capture rejection remains part
of the interface. Final functional counts are recorded in STATUS and EXP-0002:27 sealed parents,
